TypeScript has felt familiar in a lot of ways, and so far, I've enjoyed working with it. There are some differences in notation to get used to, but I like the idea of explicitly defining types and how straightforward TypeScript makes that process. Much of the code reads almost like plain English, which makes it easier to understand what is happening. Compared to my experience learning C, where everything felt much more specific and involved, TypeScript feels more approachable. Java also felt a little clunkier to me, so I appreciate how readable TypeScript can be.

From a software engineering perspective, I think TypeScript has a lot going for it. Being able to catch type errors while writing code is especially useful. Getting that feedback immediately helps prevent mistakes from becoming bigger problems later, and it feels like something that should be standard in modern development. Explicit types also make it easier to understand what a piece of code expects and what it should return, which seems valuable when maintaining software or working with other people.

I'm probably a little biased toward whatever language I've learned most recently, but TypeScript still ranks pretty high for me in terms of readability and ease of use. I'd be happy to use it more in future projects, and I can see why it's widely used. My experience so far has been positive, and I'm interested in seeing how it holds up as the projects become more complex.

Learning the language under a time limit has been a different story. I like the idea behind athletic software engineering and the practice WODs. Adding some pressure can push me to learn and improve—"pressure makes diamonds," as the saying goes. Practicing under time constraints also seems useful for technical interviews, where you have to think through a problem and apply what you know on the spot.

That said, the pressure is definitely stressful, especially when I feel like I'm not getting much guidance beforehand. Completing a WOD and then receiving an explanation afterward feels a little unorthodox to me. I can see how that approach encourages independent problem-solving, but it can also make the learning process feel more intimidating than it needs to be.

I also think there could be more flexibility in grading, particularly as the problems become more complex. Receiving no credit if you don't produce code seems harsh when someone might still have put meaningful effort into understanding the problem. Working output is a reasonable expectation for introductory exercises, but as the difficulty increases, I think the reasoning behind a solution and the quality of the code should carry more weight. Otherwise, the focus can shift toward producing something that runs rather than demonstrating good software engineering.

Overall, I still think WODs are useful for learning, and I can see this style helping me become more confident with practice. Right now, though, I find them more stressful than enjoyable. They can make me second-guess my abilities, even when I'm making progress. I think this approach could work for me, but a little more guidance and flexibility would make it easier to build confidence while still benefiting from the challenge.
